# Benchmarks

Every number on this page was measured on the machine described below with the
commands shown at the bottom. Nothing here is estimated, projected or copied
from a different workload.

## Measured on

| | |
|---|---|
| CPU | AMD Ryzen 7 255 H (8 cores / 16 threads, Zen 4c class) |
| RAM | 22.8 GB |
| Disk | KY3000-512GB, NVMe SSD |
| OS | Windows 11 Home (build 26200) |
| Toolchain | `rustc 1.98.1`, `stable-x86_64-pc-windows-gnu` |
| Profile | `[profile.bench]` — `opt-level = 3`, `lto = "thin"`, `codegen-units = 1` |
| Corpus | synthetic, deterministic, seed `0x123456789ABCDEF0` |
| Harness | Criterion 0.5, 20 samples, 6 s measurement, 1 s warm-up |

The corpus is generated by `lce_benchmarks::synthetic_store`: realistic project
tree names drawn from a fixed word list, roughly one directory per six entries,
files in the 0–50 MB range with plausible timestamps. See
[`crates/benchmarks/src/lib.rs`](../crates/benchmarks/src/lib.rs).

## File index search

`file_search/*` measures `windows_files::collect_candidates` — the exact
function `FileProvider::collect` calls. Times are Criterion's median estimate.

| benchmark | 10 000 | 100 000 | 1 000 000 |
|---|---:|---:|---:|
| `exact` ("readme") | 1.03 ms | 8.11 ms | 8.29 ms |
| `prefix` ("re") | 1.32 ms | 3.63 ms | 3.75 ms |
| `substring` ("port") | 871 µs | 7.54 ms | 7.79 ms |
| `rare_substring` ("zzqxjw") | 580 µs | 6.11 ms | 63.4 ms |
| `fuzzy` ("rpt") | 724 µs | 7.46 ms | 76.1 ms |
| `filters` (`ext:pdf` + `drive:C` + `size:>1mb`) | 544 µs | 5.92 ms | 62.4 ms |
| `path_filter` (`path:docs`) | 889 µs | 9.99 ms | – |
| `sort` (`sort:size-desc`) | 857 µs | 7.58 ms | 7.46 ms |

### Why some rows barely change between 100 000 and 1 000 000

That is not a measurement mistake, it is the candidate cap doing its job.

`collect_candidates` stops after `CANDIDATE_CAP = 4 000` matches. Queries like
`readme`, `re` and `port` match thousands of entries in the synthetic corpus, so
the scan terminates early once it has enough work for the ranker. The cost stops
growing with the index.

The rows that **do** grow are the interesting ones:

* `rare_substring` and `filters` match almost nothing, so they must visit every
  record. **A full scan of one million entries costs 62–63 ms.**
* `fuzzy` additionally runs the subsequence matcher on every candidate and
  costs **76 ms** for one million entries.

So the honest summary is:

| case | 1 000 000 entries |
|---|---|
| enough matches to hit the cap (the common typing case) | **~8 ms** |
| full scan required (rare term, or an uncommon filter) | **~62 ms** |
| full scan plus fuzzy matching on every record | **~76 ms** |

## Ranking

`ranking/*` measures `HeuristicRanker::score` over the candidate set the file
index produced. The set is capped at 4 000, so this cost is bounded regardless
of index size.

| benchmark | 10 000 | 100 000 | 1 000 000 |
|---|---:|---:|---:|
| `heuristic` (name only) | 346 µs | 3.06 ms | 2.75 ms |
| `with_usage` (usage boost enabled) | 532 µs | 3.68 ms | – |

The three numbers per row are close because the *candidate count* is what
matters, not the index size: all three corpora produce 4 000 candidates.

## Query compilation

The compiler runs before every search. It is microseconds, which is why it can
sit on the keystroke path without a second thought.

| input | median |
|---|---:|
| `query_compiler/dsl` (`type:file ext:rs modified:<24h sort:size-desc`) | 1.37 µs |
| `query_compiler/plain` (`vscode`) | 10.6 µs |
| `query_compiler/nl-process` (`正在运行的 python`) | 10.7 µs |
| `query_compiler/nl-zh` (`最近的 pdf`) | 11.2 µs |
| `query_compiler/nl-en` (`recent PDFs`) | 11.6 µs |

Plain text is slower than DSL because the natural language rules are attempted
before the input falls through to a plain keyword query.

## Index construction

`file_store/load` measures building the in-memory store from the corpus, which
is what the directory-scan backend does after `read_dir`:

| entries | median | throughput |
|---|---:|---:|
| 10 000 | 2.88 ms | 3.5 M entries/s |
| 100 000 | 30.5 ms | 3.3 M entries/s |
| 1 000 000 | 316 ms | 3.2 M entries/s |

`file_store/extension_lookup/1000000` walks every record and reads its
extension: **10.7 ms**. `file_store/stats/100000` computes file/directory counts
and the memory estimate: **103 µs**.

## Memory

Measured with `FileStore::memory_bytes()` on a fully populated store, not
estimated:

```text
1_000_000 entries
  records  : 1_000_000 × 48 B = 48.0 MB
  arena    : 21.4 MB (names, UTF-8)
  ------------------------------------
  total    : ≈ 69 MB
```

That is what the desktop UI reports in Settings → Index.

## Reproducing

```bash
cargo bench -p lce-benchmarks
```

Individual suites, or a subset of the corpus sizes:

```bash
cargo bench -p lce-benchmarks --bench file_search
cargo bench -p lce-benchmarks --bench ranking
cargo bench -p lce-benchmarks --bench file_search -- 100000
```

Criterion writes an HTML report to `target/criterion/report/index.html`.

## Caveats

* These numbers describe the **search core**, not the Windows APIs. A fresh
  process table, service list or application catalogue is not in these tables;
  see the status bar in the app, or `localsearch --providers`, for live figures
  on your own machine.
* The directory-scan backend additionally pays `read_dir` and a `stat` per
  entry; the MFT backend does not. Both then produce the same in-memory store,
  which is what is measured here.
* Numbers come from one machine. Run the benchmarks yourself before drawing
  conclusions about yours; `docs/BENCHMARKS.md` is a snapshot, not a promise.
* The first iteration of any benchmark pays page faults on a cold corpus. The
  harness warms up for a second per benchmark to damp that.
